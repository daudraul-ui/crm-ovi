# TASK 001.2: обновление и приёмка

Главный документ: [TASK-001.2.md](TASK-001.2.md). Согласованные уточнения: [TASK-001.2-decisions.md](TASK-001.2-decisions.md).

## Изменения

- Архивирование и восстановление клиентов, контактов, сетей, регионов, форматов, магазинов, проектов, задач и документов. Используемые связи защищены от удаления, включая M2M и ORM delete.
- Проект содержит основного клиента и явно выбранные дополнительные юрлица. Старые противоречивые связи не исправляются миграцией автоматически; при следующем изменении проекта их нужно явно согласовать.
- Новые/изменённые ИНН проверяются по контрольным цифрам; существующие ИНН не переписываются. Совпадения предлагается использовать, похожие сети требуют подтверждения. Форматы проверяются внутри сети.
- Версии карточек и HTTP 409 в API при устаревшем или отсутствующем version. В HTML версия передаётся скрытым полем. Документы и комментарии также версионируются.
- Резервные коды 2FA хранятся хешами, выдаются один раз, требуют пароль и резервный код для восстановления с последующей настройкой нового TOTP. Сброс администратором требует его свежий TOTP и причину; сессии отзываются. Новые коды можно получить в настройках после подтверждения TOTP.
- Редактирование сотрудников, ролей, блокировка и активация, просмотр назначенных объектов, предупреждение об открытых задачах. Защита последнего администратора и финансовых полномочий. После изменения прав/статуса сессии сотрудника отзываются.
- Семь колонок магазинов, фильтры, сортировка, URL-параметры, пагинация по 50 строк. Поиск в справочниках загружает до 50 совпадений; выбранные значения сохраняются.
- Единый XLSX: сопоставление колонок, вопросы, уточнение/исключение отдельных строк, предварительная проверка, создание связанных сущностей, согласованное обновление магазинов, повторная загрузка, атомарный откат. Финансовые данные не импортируются. Протокол и исходник доступны в контексте операции её владельцу.
- XLSX-экспорт шести реестров учитывает фильтры и права. Значения записываются строками, включая коды и строки, начинающиеся с `=`. Импортируемый шаблон доступен на странице загрузки.

## Миграции и сохранность

0005 добавляет архив, версии и дополнительные юрлица проектов. 0006 — хеши recovery-кодов. 0007 — строка блокировки операций записи. 0008–0009 — протокол импорта и уточнения строк. 0010 — версии документов/комментариев и архив документов.

Миграции только расширяют схему, не удаляют бизнес-записи, не объединяют дубли и не меняют старые связи. Уникальность новых ИНН/форматов обеспечивается валидацией под общей блокировкой записывающих запросов. Прямой SQL, bulk_update и сторонние программы должны использовать отдельный согласованный регламент: они не являются поддерживаемым пользовательским API.

## Безопасное обновление Codespaces

Сначала сохраните текущее состояние. Не меняйте DATABASE_URL, SQLITE, SECRET_KEY, PRIVATE_MEDIA_ROOT и существующие volumes. Не запускайте seed_demo на пользовательской среде ради обновления.

1. В текущем Codespaces проверьте `git status`, `git branch --show-current`, используемый движок БД и путь приватных файлов. При локальных изменениях сначала сохраните их отдельно; не используйте reset --hard.
2. Остановите запись: runserver либо web/worker/beat. Создайте новую резервную копию **базы и всех приватных файлов**, включая `imports/`. `.env` сохраните отдельно в защищённом месте.
3. Для Compose используйте существующий `scripts/backup.sh` в новом каталоге. Для SQLite после остановки приложения скопируйте фактический файл SQLite и private_media. Для PostgreSQL вне Compose сделайте pg_dump фактической БД и копию media. Не подменяйте базу пустой.
4. `git fetch origin` и `git pull --ff-only origin feat/stage-a`. При конфликте/расхождении остановитесь и сохраните обе версии.
5. В прежнем virtualenv: `pip install -r requirements.txt`, затем `python manage.py migrate --noinput`, `python manage.py bootstrap`, `python manage.py check`, `python manage.py collectstatic --noinput`.
6. Для Compose вместо локальных команд пересоберите образ (`docker compose build web`), выполните migrate/bootstrap/check через `docker compose run --rm web`, затем `docker compose up -d`.
7. Возобновите прежний процесс сервера и прежний forwarded port. Для локального HTTP runserver сохраните прежние настройки DEBUG/ALLOWED_HOSTS/CSRF_TRUSTED_ORIGINS. Обновите браузер с очисткой кеша ресурсов.
8. Сверьте количество клиентов, магазинов, проектов и файлов с копией; откройте несколько реальных карточек и скачайте документ. Проверьте историю связей. Новые функции проверяйте на отдельно созданных тестовых объектах.

При неуспехе остановите запись и восстановите согласованную пару БД+media в **отдельное окружение** для проверки. Возвращение старого кода без восстановления совместимой БД не заменяет проверенный rollback. Не применяйте обратные миграции к реальным данным без отдельного плана.

## Приёмка в интерфейсе

1. Откройте одну карточку в двух вкладках: сохраните первую, затем вторую — должно появиться предупреждение о конфликте.
2. Привяжите магазин к проекту, попробуйте удалить магазин; затем архивируйте и восстановите. Историческая связь должна остаться.
3. Создайте проект с основным и дополнительным юрлицом; чужой магазин без явного дополнительного клиента должен отклоняться.
4. Проверьте семь колонок, фильтры, сортировку и экспорт выбранных магазинов с ведущими нулями.
5. Создайте сотрудника, назначьте роль, откройте его задачи и проверьте блокировку. Не используйте единственного действующего администратора для эксперимента.
6. Получите recovery-коды на тестовой учётной записи, выполните восстановление и повторную настройку TOTP. Использованный код должен отклоняться.
7. Загрузите шаблон с новыми клиентом/сетью/магазином, ответьте на вопросы, проверьте изменения и подтвердите. Повторите файл: дублей быть не должно.
8. Проверьте повреждённый XLSX, неизвестную колонку, неверный ИНН, разные названия при совпавшем ИНН и отмену до сохранения.

## Эксплуатационные границы

- XLSX: один лист, до 10 МБ, 50 МБ распакованных данных, 10 000 строк, 30 колонок; формулы, макросы, внешние связи и вложенные активные объекты отклоняются.
- Импорт синхронный. На время анализа/сохранения запросы записи сериализуются; чтение остаётся доступным. Gunicorn timeout увеличен до 300 секунд. Для более высокой интенсивности требуется отдельный фоновый импорт с согласованными ограничениями.
- Исходники и протоколы импорта автоматически не удаляются до утверждения политики хранения; они находятся в приватном хранилище, включаются в backup и не публикуются в artifacts.
- Просмотр конкретных изменений разбит на страницы по 100, уточнение исходных строк — по 50. Полный протокол хранится в БД.
- Вопросы выдаются по 50 за одну проверку; после ответов появляются следующие. Выбор объектов, создаваемых в предпросмотре, сохраняется независимо от последовательностей PostgreSQL.
- Проверка содержимого файлов не заменяет антивирус. Для промышленного окружения настройте `DOCUMENT_SCANNER` на доверенный исполняемый файл: один аргумент — путь карантинного файла, exit 0 означает принятие; ошибка/тайм-аут отклоняет загрузку. Карантин — временный приватный каталог до сохранения в media.
- БП-01/02/03+, финансовые процессы, VPS/TLS и автоматическое слияние PR не входят в реализацию. Окончательную пользовательскую приёмку выполняет владелец CRM.
