# CRM OVI v0.1 — БП-01/02: эксплуатация и безопасное обновление

Изменения продолжают TASK 001.2 A–D в `feat/stage-a`, PR #1. Предыдущие справочники, Excel, сотрудники и данные сохранены. Матрица требований: [REQUIREMENTS-BP01-BP02.md](REQUIREMENTS-BP01-BP02.md).

## Что реализовано

Новый раздел **Продажи и производство** (`/workflow/`) объединяет обращения, технические спецификации и оборудование, версии КП, калькуляции и распределения затрат, согласования, утверждённую экономику, заказы поставщикам, условия запуска, партии и письменные подтверждения. Все команды HTML и JSON используют один транзакционный слой, контроль версии и серверные роли.

БП-02: зафиксируйте обращение и следующий шаг; добавьте ТЗ и позиции по магазинам. Ненадёжные размеры, нестандартное оборудование, требование клиента/тендера или решение сотрудника требуют документа замеров. ТЗ подтверждают менеджер и инженер. Изменения подтверждённого ТЗ создаются новой редакцией. Укажите клиентские строки, затраты по обязательным категориям (нулевые, если не применяются; шеф-монтаж опционален), распределите каждую статью без двойного учёта. РОП/директор устанавливает коммерческий минимум. Сумма согласования считается с НДС: менее 3 млн — один руководитель, от 3 млн — два разных; искусственное разделение и маржа ниже минимума также требуют обоих. Отказ открывает совместное обсуждение, после него новый раунд. Исключение разрешает руководитель с документом и причиной; статус остаётся «НЕ СОГЛАСОВАНО».

Внутреннее КП показывает себестоимость, прибыль и маржу. Клиентские PDF/XLSX содержат только клиентские строки и НДС; три режима отображения используют один расчёт Decimal. При регистрации отправки прикладывается подтверждающий документ и выбирается будущая дата follow-up. Точные отправленные файлы сохраняются в БД: последующие согласования не изменяют прошлую отправку. Новая редакция требует согласования заново. Отправку писем система сама не выполняет.

База экономики фиксируется по документу подтверждения заказа/договора, отдельно для каждого заказа. Заменить её может только согласованная редакция того же заказа с подтверждённым изменением клиентом цены, объёма или состава. Внутренний перерасход меняет прогноз/факт. Падение прогноза более 5 п.п. уведомляет РОПа; прогноз ниже коммерческого минимума требует решений обоих руководителей, новая редакция прогноза сбрасывает прежние решения. Фиксация фактических расходов не скрывается из-за отсутствия согласования. KPI считает финансово завершённые проекты: цель ≥90% с падением маржи ≤5 п.п.; неполные данные не засчитываются как успех.

БП-01: создайте партии с позициями ТЗ и индивидуальными условиями запуска. Платёжное поручение проверяется по сумме, плательщику, получателю, реквизитам заказа и исполнению. Это основание запуска, а не подтверждение фактического зачисления. После всех условий менеджер явно разрешает запуск: создаётся задача размещения не позднее двух рабочих дней. Отправка поставщику требует документа. Менеджер проекта проверяет письмо поставщика: email, дату получения, документ, состав, дополнительное количество и срок готовности. Частичные подтверждения сохраняются отдельно и не закрывают контроль остальных позиций. Запрос остановки не означает остановку; до письменного подтверждения затронутые позиции остаются в производстве, действия согласуются с клиентом и РОПом.

Celery Worker + Beat контролируют размещение, неподтверждённые партии, деньги, КП и follow-up. После отправки поставщику: день 1 — менеджер, день 2 — менеджер+РОП, день 3 и далее — также директор, с ежедневной дедупликацией. Пауза требует запроса с причиной и согласования РОПа, ограничена настройкой календаря; она не скрывает контроль поступления денег. Перенос срока размещения допускается РОПом/директором с причиной. Инциденты и персональные уведомления доступны в CRM; внешние email/SMS-каналы не подключены.

## Роли и история

- Менеджер проекта ведёт свои бизнес-команды; РОП может замещать его, с историей исполнителя и исходного ответственного. Подтверждать письмо поставщика может только назначенный менеджер проекта.
- Инженер работает с ТЗ/оборудованием, подтверждает техническую часть; коммерческая экономика закрыта.
- Менеджер, РОП и директор получают отдельное `workflow.view_economics` через `bootstrap`. Это не расширяет старое `crm.view_finance` для произвольных финансовых заметок.
- При смене менеджера РОП выполняет передачу из обращения/ТЗ. Открытые задачи прежнего менеджера сначала поступают РОПу, затем он распределяет их через существующий реестр задач; выполненные задачи сохраняют исполнителя. Прямое изменение менеджера такого проекта заблокировано.
- Решения, подтверждения и история доступны для чтения. Удаление возможно только для разрешённых строк черновика с отдельным подтверждением. Используемые проекты/магазины/документы защищены связями; магазин нельзя отсоединить от проекта, если он используется в ТЗ/КП.

## Настройка перед приёмкой

РОП/директор создаёт рабочий календарь: часовой пояс IANA, время ежедневной проверки, максимум паузы, день первого напоминания КП. Команда заполнения диапазона требует явного выбора рабочих дней недели и исключений. Уже заданные даты не перезаписываются. Все календарные даты диапазона должны существовать, включая выходные; при пробеле CRM останавливает расчёт и сообщает руководителям. Демонстрационный календарь не является утверждённым производственным календарём.

Техническая интерпретация срока: день события — день 0 в часовом поясе календаря, срок наступает во время проверки на N-й последующий рабочий день. Подтвердите это правило и параметры календаря на пользовательской приёмке. Интервал опроса Beat — 300 секунд (`BUSINESS_NOTIFICATION_INTERVAL`), он не заменяет рабочий календарь. Запускать один экземпляр Beat.

Фирменный шаблон КП отсутствует в доступных исходных материалах: реализована нейтральная форма OVI с кириллицей, проверенными итогами и маркировкой. Фирменное оформление, утверждённый календарь/паузы/время напоминаний и приёмка владельцем остаются условиями выпуска. VPS, домен и production deploy в этом PR не выполняются. Черновые БП-03/04 и прочие последующие процессы не реализованы.

## API

Подтверждённая TOTP-сессия, session cookie и CSRF обязательны. `/api/workflow/<resource>/` — GET/POST; `/<id>/` — GET/PATCH; `/<id>/<command>/` — POST. Команда содержит `version`; PATCH — `expected_version`. Конфликт возвращает 409, неверные данные 400, недостаточные права 403. Неизвестные/защищённые поля отклоняются. Списки и история пагинированы по 30: `/<id>/history/` — GET.

Ресурсы: `inquiries`, `specifications`, `equipment`, `quotes`, `quote-lines`, `costs`, `allocations`, `orders`, `order-lines`, `conditions`, `calendars`, `calendar-days`, `budgets`. `decisions`, `confirmations`, `budget-decisions` доступны только для чтения. Схемы полей и бизнес-команд находятся в `workflow/forms.py`; HTML-формы показывают те же обязательные поля. Клиентский экспорт: `/workflow/quotes/<id>/export/pdf/` и `.../xlsx/`. Документ-основание предварительно загружается через существующий защищённый модуль документов CRM.

## Безопасное обновление Codespaces с PostgreSQL/Compose

Сначала проверьте `git status --short` и сохраните незакоммиченные изменения отдельно. Не применяйте `reset --hard`, не удаляйте БД, volumes или `.env`. Команды ниже относятся к существующему тестовому Codespace, не к production.

1. Сохраните текущий commit (`git rev-parse HEAD`) и защищённую копию `.env` вне репозитория. Остановите запись в приложение и фоновые процессы. Сохраните PostgreSQL и приватные файлы одним комплектом:

   ```sh
   docker compose stop web worker beat
   ./scripts/backup.sh "backups/pre-bp01-bp02-$(date +%Y%m%d-%H%M%S)"
   ```

   Скрипт отказывается перезаписывать существующий каталог. Скопируйте резервную копию в защищённое хранилище вне Codespace. До обновления рабочей БД проверьте восстановление на отдельном Compose project с отдельными volumes и портами; используйте `scripts/restore.sh` только для этого отдельного проекта. Не восстанавливайте поверх пользовательских данных для проверки.

2. Получите изменения без переписывания истории:

   ```sh
   git fetch origin
   git switch feat/stage-a
   git pull --ff-only origin feat/stage-a
   docker compose build web
   docker compose run --rm web python manage.py migrate --plan
   docker compose run --rm web python manage.py migrate --noinput
   docker compose run --rm web python manage.py bootstrap
   docker compose run --rm web python manage.py check
   docker compose up -d --no-build
   docker compose ps
   ```

   Миграции workflow создают новые таблицы и поля, не удаляют/не переименовывают данные CRM. `bootstrap` обновляет права существующих групп. Статика собирается при сборке образа. Секреты и существующие volumes сохраняются. Команду `seed_demo` и CI-фикстуры на этой БД не запускайте.

3. Проверьте вход с TOTP, прежние клиенты/сети/магазины и документы, `/workflow/`, доступ инженера, роли согласования, создание календаря. На копии данных проведите оба сквозных сценария, отказ, исключительную отправку, частичную партию, паузу и просрочку. Зафиксируйте результаты в протоколе приёмки.

При проблемах держите запись остановленной. Не откатывайте миграции workflow с удалением таблиц. Сохраните комплект текущих данных и журналов; предыдущий образ можно использовать только после проверки совместимости с расширенной схемой. Восстановление резервной копии в пользовательскую БД — отдельная операция с согласованным окном и возможной потерей новых данных.

## Codespaces с SQLite

Остановите Django и все пишущие процессы. Сохраните `.env`, весь каталог приватных документов и текущую SQLite через `sqlite3.Connection.backup()` в новый файл (не поверх существующего); штатный путь `work/dev.sqlite3`, либо явный `SQLITE_DB_PATH`. Проверьте копию (`PRAGMA integrity_check`). На отдельной копии сначала выполните миграции и проверки. После `git pull --ff-only`, активации `.venv` и `pip install -r requirements.txt` выполните `migrate --plan`, `migrate`, `bootstrap`, `check`, затем запускайте сервер. SQLite пригодна для разработки; рабочие блокировки и конкурентные согласования проверяются на PostgreSQL.
