# 3. TASK 001.2A — Безопасность и целостность данных

## 3.1. Контроль удаления объектов

Для клиентов, торговых сетей, магазинов, проектов, форматов и иных значимых объектов реализовать безопасную модель жизненного цикла.

Требования:

- Если объект используется другими объектами, физическое удаление должно быть запрещено.
- Предусмотреть архивирование вместо удаления.
- Архивный объект не должен исчезать из истории проектов.
- Существующие связи должны сохраняться.
- При попытке удаления показывать понятное сообщение со списком зависимостей.
- Возможность восстановления объекта из архива.
- Все операции архивирования и восстановления фиксировать в аудите.

Архивирование не должно автоматически отменять существующие задачи или менять состояние проектов.

## 3.2. Контроль связей между клиентами, торговыми сетями и магазинами

Сохранить утверждённую модель:

**Клиент (юридическое лицо) ↔ Торговая сеть → Магазин.**

Одна торговая сеть может иметь несколько юридических лиц.

Одно юридическое лицо может быть связано с несколькими торговыми сетями, если это разрешено структурой данных.

Для магазина:

- торговая сеть обязательна;
- клиент выбирается только из юридических лиц, связанных с выбранной торговой сетью;
- клиент может быть не указан, если достоверной информации пока нет;
- регион выбирается из общего справочника;
- формат выбирается из справочника соответствующей сети;
- код магазина уникален внутри торговой сети.

Для проекта:

- проверять согласованность магазинов и юридического лица проекта;
- поддерживать проекты с несколькими магазинами;
- не допускать незаметного присоединения магазинов с противоречивыми юридическими связями;
- не блокировать потенциально допустимые сетевые проекты с несколькими юридическими лицами без согласования бизнес-правила.

Если текущая модель проекта не позволяет корректно представить согласованный реальный сценарий, Codex должен сначала предложить варианты изменения модели с анализом миграций и влияния на интерфейс.

## 3.3. Контроль дублирования

**Клиенты:**

- основной идентификатор — ИНН;
- проверять допустимую длину и контрольные цифры ИНН для российских организаций и ИП;
- сохранять возможность отсутствия ИНН;
- при совпадении ИНН предлагать существующую запись;
- не создавать дубликат без явного решения пользователя;
- не объединять существующие записи автоматически.

**Торговые сети:**

- нормализовать название для поиска совпадений;
- учитывать регистр и лишние пробелы;
- при похожих названиях предупреждать о потенциальном дублировании;
- не считать каждое похожее название безусловным дубликатом.

**Магазины:**

- уникальность по сочетанию торговой сети и кода магазина;
- код хранить строкой;
- сохранять ведущие нули;
- проверять повторную загрузку существующих магазинов.

**Форматы:**

- предотвращать точные дубликаты внутри одной торговой сети;
- одинаковое название формата в разных сетях допустимо.

**Регионы:**

- использовать глобальный справочник;
- предотвращать дубликаты с учётом нормализации;
- сохранить существующие записи и исторические связи.

## 3.4. Защита от конфликтов одновременного редактирования

Если два сотрудника открыли одну карточку и изменяют её одновременно, CRM не должна молча перезаписывать чужие изменения.

Реализовать:

- версию или временную метку изменения записи;
- проверку актуальности при сохранении;
- предупреждение о конфликте;
- возможность обновить карточку и повторить редактирование;
- безопасную обработку конфликта в REST API.

## 3.5. Двухфакторная авторизация

Сохранить обязательную 2FA.

Дополнительно:

- безопасное восстановление доступа при потере приложения-аутентификатора;
- одноразовые резервные коды;
- хранение резервных кодов только в виде защищённых хешей;
- защищённая процедура административного сброса;
- проверка полномочий;
- журналирование сброса и восстановления;
- завершение действующих сессий при компрометации 2FA;
- защита от частых попыток ввода кодов.

Не создавать обходных способов входа по одному паролю.

## 3.6. Безопасность документов

Для загружаемых файлов:

- проверка расширения;
- проверка фактического формата и содержимого;
- ограничения размера;
- предотвращение исполнения загруженных файлов;
- хранение вне публичной директории;
- проверка прав при каждом скачивании;
- журналирование скачиваний;
- защита от повреждённых или вредоносных файлов.

Для будущей промышленной среды предусмотреть антивирусную проверку и изоляцию подозрительных загрузок.

## 3.7. Демонстрационные данные

Обновить `seed_demo`, чтобы тестовые объекты соответствовали актуальной модели связей.

Не изменять существующие реальные или пользовательские записи при запуске генератора.

# 4. TASK 001.2B — Интерфейс и справочники

## 4.1. Управление сотрудниками

Раздел «Настройки → Сотрудники».

Возможности:

- создание сотрудника;
- редактирование имени, фамилии, логина и контактных данных;
- назначение одной или нескольких ролей;
- изменение ролей;
- блокировка и повторная активация;
- просмотр статуса сотрудника;
- просмотр назначенных клиентов, проектов и задач;
- контроль открытых задач при блокировке;
- журнал изменений прав и статуса.

Сохраняемые роли:

- Директор;
- РОП;
- Менеджер;
- Инженер;
- Администратор.

Подрядчики и дополнительные роли не создаются автоматически в рамках TASK 001.2.

Право редактирования сотрудников выдавать только уполномоченным ролям.

Администратор без финансовых полномочий не должен получать или выдавать финансовые права через обходные сценарии.

Не допускать лишения системы последнего действующего пользователя с необходимыми административными полномочиями.

## 4.2. Назначение менеджеров

В карточке клиента должно быть поле «Ответственный менеджер».

Требования:

- выбирать сотрудника из справочника;
- показывать имя и фамилию, а не только логин или ID;
- предусмотреть поиск сотрудника;
- не назначать заблокированного пользователя;
- учитывать назначенные роли;
- сохранять историю изменения ответственного;
- предупреждать о незавершённых задачах при блокировке менеджера.

## 4.3. Реестр клиентов

Отображать полезную информацию без необходимости открывать каждую карточку.

Базовые колонки:

1. Название юридического лица.
2. ИНН.
3. Ответственный менеджер.
4. Связанные торговые сети.
5. Статус.
6. Действия.

Функции:

- поиск по названию и ИНН;
- фильтр по ответственному менеджеру;
- фильтр по торговой сети;
- сортировка;
- открытие карточки;
- редактирование;
- экспорт Excel.

Поля, для которых отсутствуют данные, показывать прочерком.

## 4.4. Реестр магазинов

**Окончательно согласованная структура.**

Отображать колонки строго в указанном порядке:

1. **Номер (КОД)**
2. **Название**
3. **Адрес**
4. **Регион**
5. **Формат**
6. **Торговая сеть**
7. **Клиент (юридическое лицо)**

Справа — отдельная колонка «Действия».

Требования:

- код и название кликабельны;
- открывают карточку соответствующего магазина;
- кнопка «Изменить» находится отдельно;
- незаполненные значения отображаются прочерком;
- названия регионов, форматов, сетей и клиентов выводятся корректно;
- не объединять несколько атрибутов в одну колонку «Сведения».

Поиск, фильтры и сортировка должны работать по всем семи полям.

Фильтры по региону, формату, торговой сети и клиенту должны использовать справочники, а не требовать ввода внутренних ID.

Добавить:

- сброс фильтров;
- сохранение параметров поиска в URL;
- серверную пагинацию;
- понятное отображение общего количества записей;
- горизонтальную прокрутку таблицы на небольших экранах.

Для списков с большим количеством записей избегать загрузки всех объектов в браузер одновременно.

## 4.5. Карточка магазина

Поля:

- Номер (КОД);
- Название;
- Адрес;
- Регион;
- Формат;
- Торговая сеть;
- Клиент (юридическое лицо).

Поведение:

1. Пользователь выбирает торговую сеть.
2. CRM автоматически обновляет доступные юридические лица этой сети.
3. CRM автоматически обновляет доступные форматы этой сети.
4. Справочник регионов остаётся общим и не зависит от сети.
5. Пользователь может создать новый формат прямо из карточки магазина.
6. После создания формата введённые данные магазина не теряются.
7. Если к сети не привязано ни одного клиента, система показывает объяснение и ссылку на редактирование торговой сети.
8. Если смена сети делает текущего клиента или формат недопустимым, CRM предупреждает об этом.
9. Сохранять корректную валидацию на сервере, независимо от JavaScript.

Не изменять существующие записи при открытии или просмотре формы.

## 4.6. Торговые сети

Сохранить поддержку нескольких юридических лиц.

Карточка торговой сети должна содержать:

- список магазинов;
- список форматов;

- действия редактирования.

При попытке удалить связь с юридическим лицом, которое уже используется магазином, показывать понятное предупреждение.

Не разрывать связанные данные автоматически.

## 4.7. Общий справочник регионов

Регион является глобальной сущностью, доступной всем торговым сетям.

Не создавать отдельные региональные справочники для каждой сети.

## 4.8. Форматы магазинов

# 5. TASK 001.2C — Единый интеллектуальный импорт Excel

## 5.1. Основное требование

**Один Excel-файл должен позволять автоматически создавать все необходимые связанные объекты CRM.**

Не требовать предварительного ручного создания клиентов, сетей, регионов, форматов и магазинов.

Поддерживать формат `.xlsx`.

## 5.2. Объекты для импорта

Обязательная поддержка:

- клиенты (юридические лица);
- торговые сети;
- регионы;
- форматы магазинов;
- магазины;
- связи между перечисленными объектами.

Дополнительная поддержка:

- контактные лица;
- назначение ответственного менеджера, если сотрудник уже существует и однозначно определяется.

Не создавать сотрудников автоматически из Excel без отдельного согласования.

Импорт проектов и задач оставить за пределами текущего задания, поскольку для них необходима отдельная согласованная структура данных.

## 5.3. Пример структуры Excel

Таблица может содержать следующие колонки:

| Колонка | Назначение |
|---|---|
| Торговая сеть | Название сети |
| Клиент | Наименование юридического лица |
| ИНН | Идентификатор юридического лица |
| Номер (КОД) | Код магазина внутри сети |
| Название | Название магазина |
| Адрес | Адрес магазина |
| Регион | Регион магазина |
| Формат | Формат магазина |
| Менеджер | Ответственный сотрудник |
| Контактное лицо | ФИО контактного лица |
| Телефон | Телефон контакта |
| Email | Электронная почта |

Не все колонки обязательны для каждой строки.

Обязательность определяется типом создаваемого объекта и утверждёнными правилами CRM.

## 5.4. Распознавание колонок

Импорт должен понимать распространённые названия:

- «Код», «Код ТТ», «Номер магазина», «Номер ТТ»;
- «ТС», «Сеть», «Торговая сеть»;
- «ЮЛ», «Юридическое лицо», «Клиент»;
- «Адрес», «Адрес ТТ», «Адрес магазина».

Также необходим интерфейс ручного сопоставления колонок.

Если CRM не понимает колонку, она должна спросить пользователя, как её трактовать.

Не угадывать неоднозначные поля без подтверждения.

## 5.5. Автоматическое создание объектов

После чтения файла система должна:

1. Найти существующие торговые сети.
2. Найти существующие юридические лица.
3. Определить необходимые связи между сетями и юридическими лицами.
4. Найти или создать регионы.
5. Найти или создать форматы в соответствующих сетях.
6. Найти существующие магазины.
7. Подготовить создание новых магазинов.
8. Назначить допустимые юридические лица магазинам.
9. Проверить отсутствие конфликтов.
10. Сформировать предварительный результат.

При повторном импорте одного и того же файла дубли не должны создаваться.

## 5.6. Уточняющие вопросы

Если данных недостаточно, CRM должна задавать вопросы до сохранения.

Примеры:

**Ситуация 1.** У торговой сети несколько юридических лиц, но у магазина не указан клиент.

Варианты:

- выбрать одно юридическое лицо;
- назначить разные юридические лица для отдельных строк;
- оставить поле пустым, если это разрешено моделью;
- исключить спорные строки из импорта.

**Ситуация 2.** Указана торговая сеть, название которой похоже на существующую.

Варианты:

- использовать существующую;
- создать новую;
- пропустить соответствующие строки.

**Ситуация 3.** Магазин с данным кодом уже существует.

Варианты:

- оставить существующий;
- показать различия;
- обновить разрешённые поля;
- пропустить запись.

**Ситуация 4.** Не указан регион или формат.

Варианты:

- выбрать из справочника;
- создать новый;
- оставить пустым, если поле необязательное.

**Ситуация 5.** Клиент с таким ИНН уже существует под другим названием.

Показать обе записи и различия, предложить использовать существующего клиента либо отложить решение.

Одинаковые вопросы группировать.

Не показывать сотни повторяющихся диалогов для одинаковых ситуаций.

## 5.7. Предварительный просмотр

- количество новых клиентов;

- количество новых регионов;
- количество новых форматов;
- количество новых магазинов;
- количество новых связей;
- количество обновлений;
- количество пропусков;
- количество ошибок;
- количество вопросов, требующих решения.

Предусмотреть просмотр конкретных изменений.

## 5.8. Режимы импорта

**Режим 1 — Создание недостающих объектов.**

Существующие записи не изменять.

**Режим 2 — Создание и обновление.**

Обновлять только согласованные поля после подтверждения пользователя.

**Режим 3 — Проверка без сохранения.**

Выполнять анализ файла, показывать ошибки и предполагаемые изменения без записи в базу.

Режим обновления не должен перезаписывать непустые данные пустыми значениями без явного подтверждения.

## 5.9. Целостность операции

Использовать транзакционное сохранение.

Если возникает критическая ошибка, импорт должен быть отменён без частично созданных объектов.

Повторный запуск после ошибки должен быть безопасным.

Для одновременных импортов предусмотреть защиту от дублирования.

## 5.10. Протокол импорта

Сохранять:

- пользователя;
- дату и время;
- имя и защищённую копию исходного файла согласно политике хранения;
- выбранные режимы;
- результаты предварительной проверки;
- ответы на уточняющие вопросы;
- итоговое количество созданных и обновлённых записей;
- ошибки и пропуски;
- идентификатор операции.

Содержимое файла не должно попадать в открытые системные журналы и не должно быть доступно пользователям без соответствующих прав.

## 5.11. Производительность и безопасность Excel

- Ограничивать размер файла и распакованных данных.
- Ограничивать число строк и колонок.
- Не исполнять макросы.
- Проверять структуру XLSX.
- Корректно обрабатывать повреждённые файлы.
- Отображать понятные ошибки.
- Сохранять коды магазинов как строки.
- Не превращать значения, начинающиеся с нуля, в числа.
- Предупреждать о кодах, которые Excel уже преобразовал численно и исходное представление которых восстановить невозможно.

Необходимо обеспечить корректную работу как минимум с файлами на 1 000 и 10 000 строк в рамках согласованных ограничений производительности.
