# CRM OVI — этап A

Работающая основа CRM продаж и проектов остекления холодильного оборудования. Python 3.12, Django 5.2 LTS, DRF, PostgreSQL 17, Redis 7.4, Celery, Django Templates, HTMX 2, Alpine 3, Tailwind 4, Gunicorn, Caddy. Точные Python-версии зафиксированы в `requirements.txt`, frontend — в `package-lock.json`. JS и собранный CSS локальные, CDN при работе приложения не требуется.

## Запуск Docker Compose

```sh
cp .env.example .env
# Замените SECRET_KEY и POSTGRES_PASSWORD, согласуйте пароль в DATABASE_URL.
# Для домена установите CRM_DOMAIN, ALLOWED_HOSTS и CSRF_TRUSTED_ORIGINS.
docker compose build
docker compose up -d db redis
docker compose run --rm web python manage.py migrate --noinput
docker compose run --rm web python manage.py bootstrap
docker compose run --rm web python manage.py create_account director --email director@example.org --role Директор
docker compose up -d
```

Открыть `https://localhost` (для локального сертификата Caddy потребуется доверие к его CA). На публичном домене Caddy получает TLS-сертификат автоматически. Пароль аккаунта вводится скрыто. При первом входе добавьте показанный `otpauth://` адрес в приложение TOTP (можно извлечь параметр `secret` и ввести вручную), подтвердите текущий код. До подтверждения кода все страницы и API закрыты. Повторное использование кода блокируется; неверные TOTP имеют задержку django-otp. Вход ограничен десятью неудачными попытками на пару IP/логин за 15 минут через Redis. Backend web не публикуется наружу: доверенный TLS proxy — Caddy.

Секреты не коммитить. Для пароля PostgreSQL с особыми символами используйте URL-кодирование в DATABASE_URL. Смена POSTGRES_PASSWORD после инициализации volume сама по себе не меняет пароль в БД. Запускайте миграции до запуска worker/beat; единственный экземпляр Beat.

### Демонстрационные данные

```sh
# Выберите собственный пароль (не короче 12 символов).
read -s DEMO_PASSWORD
export DEMO_PASSWORD
docker compose run --rm -e DEMO_PASSWORD web python manage.py seed_demo
unset DEMO_PASSWORD
```

Аккаунт `demo`, роль директор, клиент, сеть, магазин, проект и задача. Повторный запуск не сбрасывает пароль существующего аккаунта. Только в тестовом окружении.

## Локальная разработка

```sh
python3.12 -m venv .venv
. .venv/bin/activate
pip install -r requirements.txt
mkdir -p work
export SQLITE=1 DEBUG=1
python manage.py migrate
python manage.py bootstrap
python manage.py create_account developer --email developer@example.org --role Директор
python manage.py runserver
```

SQLite — дополнительный режим разработки; production и CI используют PostgreSQL. Для локального PostgreSQL уберите SQLITE и установите DATABASE_URL. DEBUG=1 нужен для локального HTTP; production cookies имеют Secure. При тестировании PostgreSQL без Redis укажите TESTING=1 (подменяет только cache).

Frontend: `npm ci && mkdir -p work && npm run build`. Собранный `static/app.css` включён в git, Node в runtime не нужен. Исходный дополнительный стиль — `static/custom.css`. HTMX отвечает за поиск без полной перезагрузки; Alpine — мобильную навигацию.

## Модули

- Пользователи: Django personal accounts, обязательное подключение TOTP, серверная проверка прав, несколько ролей через группы.
- Клиенты: компании, ИНН (10/12 цифр), реквизиты, контакты, менеджеры, поиск по названию/ИНН, фильтр по менеджеру.
- Сети: сеть → регион / формат → магазин; адреса, коды, уникальность кода внутри сети, проверка принадлежности справочников.
- Проекты: клиент, менеджер, несколько магазинов, статусы, комментарии, документы; карточка со связанными данными.
- Задачи: исполнитель, срок, приоритет, статусы, переназначение, просрочки, история изменений.
- Документы: случайные имена, whitelist расширений, лимит 10 МБ, приватный volume, скачивание как attachment после проверки прав документа и связанных сущностей; пути не возвращаются в API.
- Уведомления: персональный центр, отметка прочтения, уведомления назначений и просрочек (Celery Beat каждые 5 минут, дедупликация). Интерфейс `NotificationChannel` для будущих адаптеров, внешняя доставка пока отсутствует.
- Аудит: создание, изменение, удаление, импорт, скачивание, успешные этапы входа; before/after, автор и время. Финансовые тексты, реквизиты и контактные данные редактируются в аудите. Журнал доступен в настройках, история — в карточках для уполномоченных пользователей.
- Главная: реальные счётчики БД, проекты, просроченные задачи.

### Матрица доступа

| Роль | Права |
|---|---|
| Директор | Все операции CRM, финансовое разрешение, чтение аудита |
| РОП | CRUD CRM, без финансов и журнала аудита |
| Менеджер | Чтение/создание/изменение CRM, без удаления, финансов и журнала аудита |
| Инженер | Чтение проектов/магазинов/сетей/задач/документов/комментариев, изменение задач, создание/изменение комментариев |
| Администратор | Все операции CRM и чтение аудита, без финансов |

Права суммируются для нескольких ролей. Отдельное разрешение `crm.view_finance` разрешает чтение и изменение `financial_notes`; проверяется в HTML и API. Назначенный менеджер — атрибут ответственности: на этапе A нет изоляции записей по владельцу, роли имеют доступ ко всем записям разрешённых модулей. Личные уведомления изолированы по пользователю. Пользователи без роли не видят данные CRM. Superuser — доверенный технический оператор с полными правами; ему также требуется TOTP. Интерфейс Django admin намеренно не подключён.

Аккаунты создаются `create_account`, роли обновляются идемпотентной командой `bootstrap`. Изменение ролей/блокировка существующих пользователей выполняется доверенным оператором через Django shell; самостоятельного редактора пользователей пока нет. При утрате TOTP доверенный оператор удаляет устройство пользователя через shell, завершает его сессии и регистрирует операцию в AuditEvent; автоматического сброса по email нет. Изменения напрямую через shell/SQL не перехватываются приложением.

### Импорт магазинов

`/stores/import/`, XLSX до 2 МБ, не более 1000 строк, распакованный архив до 20 МБ. Заголовки строго: `Сеть | Код | Название | Адрес | Регион | Формат`. Сеть обязательна, регион и формат необязательны и должны существовать в выбранной сети. Код храните в Excel как текст для сохранения начальных нулей. Любая ошибочная строка отменяет весь импорт; дубликаты не обновляются автоматически.

### API

Session authentication + CSRF + подтверждённая TOTP-сессия, тех же серверных прав достаточно и для HTML. Базовый URL `/api/` с ресурсами:
`companies`, `contacts`, `chains`, `regions`, `formats`, `stores`, `projects`, `tasks`, `documents`, `comments`.
GET / POST / PUT / PATCH / DELETE; списки по 30 записей. Загрузка документов — multipart POST; скачивание только `/documents/<id>/download/`. Финансовые поля скрыты без специального разрешения; попытка изменить их через API возвращает 403. История аудита не имеет API для редактирования/удаления. Справочник пользователей не публикуется.

## Проверки

```sh
SQLITE=1 DEBUG=1 pytest
# PostgreSQL (пользователь должен иметь CREATEDB для тестовой базы):
DATABASE_URL=postgresql://crm:password@localhost:5432/crm DEBUG=1 TESTING=1 pytest
python manage.py makemigrations --check --dry-run
python manage.py check
```

Тесты проверяют пароль/TOTP, первичную настройку и replay кода, анонимный доступ, отсутствие роли, несколько ролей, финансовые права, CRUD HTML/API, связи магазинов, переназначение/историю, защищённые файлы, изоляцию уведомлений, импорт с rollback, CSRF, аудит, миграции и страницы. GitHub Actions выполняет тесты с PostgreSQL 17 и Python 3.12. Результаты текущего прогона — `docs/validation.md`.

## Резервное копирование

```sh
scripts/backup.sh backups/manual
# Восстановление только из доверенного архива, заменяет БД:
CONFIRM_RESTORE=YES scripts/restore.sh backups/manual
```

Архив содержит pg_dump custom format и приватные файлы. Перед согласованным backup остановите запись: `docker compose stop web worker beat`, затем запустите backup и возобновите сервисы. Настройте внешнее расписание, шифрование архивов и хранение вне сервера. `.env` и ключи резервируются отдельно защищённым способом. Restore останавливает web/worker/beat; при ошибке они остаются остановленными для проверки оператором.

## Границы этапа A

БП-01/БП-02 не реализованы: предусмотрены базовые сущности, права, статусы и сервисный слой. БП-03 и следующие процессы отсутствуют. Нет самостоятельных договоров, логистики, монтажа, бухгалтерии, банковских интеграций, Telegram/Email доставки. Нет финансового учёта: отдельное защищённое текстовое поле демонстрирует границу финансового доступа.

Это основа для внутреннего пилота после настройки инфраструктуры и ролей. До промышленной эксплуатации нужны согласование матрицы доступа, политика восстановления 2FA и паролей, антивирусная проверка файлов (сейчас есть ограничения типа/размера, скачивание принудительное), мониторинг, квоты хранилища, offsite backup и регулярная проверка восстановления. Полнотекстовый поиск, расширенная фильтрация API и страницы списков свыше 200 строк оставлены на следующий этап; API имеет пагинацию. Не проводился нагрузочный тест или независимый аудит безопасности.

## Структура изменений

- `config/`: настройки Django, маршруты, WSGI, Celery.
- `crm/models.py`, `migrations/`: модели и начальная схема.
- `crm/security.py`, `forms.py`, `views.py`, `api.py`: права, формы, UI и REST.
- `crm/services.py`, `tasks.py`: аудит, уведомления, периодические задачи.
- `crm/management/commands/`: роли, персональные аккаунты, демоданные.
- `templates/`, `static/`: адаптивный русский интерфейс и локальные frontend-ресурсы.
- `tests/`, `pytest.ini`, `.github/workflows/tests.yml`: тесты и CI.
- `Dockerfile`, `compose.yaml`, `Caddyfile`, `.env.example`, `scripts/`: runtime и обслуживание.

Изменения предназначены для PR в main; автоматическое слияние не выполняется.
