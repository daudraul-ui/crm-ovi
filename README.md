# CRM OVI — этап A

Работающая основа CRM продаж и проектов остекления холодильного оборудования. Python 3.12, Django 5.2 LTS, DRF, PostgreSQL 17, Redis 7.4, Celery, Django Templates, HTMX 2, Alpine 3, Tailwind 4, Gunicorn, Caddy. Точные Python-версии зафиксированы в `requirements.txt`, frontend — в `package-lock.json`. JS и собранный CSS локальные, CDN при работе приложения не требуется.

## Запуск Docker Compose

```sh
cp .env.example .env
# Замените SECRET_KEY и POSTGRES_PASSWORD, согласуйте пароль в DATABASE_URL.
# Для домена установите CRM_DOMAIN, ALLOWED_HOSTS и CSRF_TRUSTED_ORIGINS.
docker compose build
docker compose up -d db redis
docker compose run --rm web python manage.py migrate --noinput
docker compose run --rm web python manage.py bootstrap
docker compose run --rm web python manage.py create_account director --email director@example.org --role Директор
docker compose up -d
```

Открыть `https://localhost` (для локального сертификата Caddy потребуется доверие к его CA). На публичном домене Caddy получает TLS-сертификат автоматически. Пароль аккаунта вводится скрыто. При первом входе добавьте показанный `otpauth://` адрес в приложение TOTP (можно извлечь параметр `secret` и ввести вручную), подтвердите текущий код. До подтверждения кода все страницы и API закрыты. Повторное использование кода блокируется; неверные TOTP имеют задержку django-otp. Вход ограничен десятью неудачными попытками на пару IP/логин за 15 минут через Redis. Backend web не публикуется наружу: доверенный TLS proxy — Caddy.

Секреты не коммитить. Для пароля PostgreSQL с особыми символами используйте URL-кодирование в DATABASE_URL. Смена POSTGRES_PASSWORD после инициализации volume сама по себе не меняет пароль в БД. Запускайте миграции до запуска worker/beat; единственный экземпляр Beat.

### Демонстрационные данные

```sh
# Выберите собственный пароль (не короче 12 символов).
read -s DEMO_PASSWORD
export DEMO_PASSWORD
docker compose run --rm -e DEMO_PASSWORD web python manage.py seed_demo
unset DEMO_PASSWORD
```

Аккаунт `demo`, роль директор, клиент, сеть, магазин, проект и задача. Повторный запуск не сбрасывает пароль существующего аккаунта. Только в тестовом окружении.

## Локальная разработка

```sh
python3.12 -m venv .venv
. .venv/bin/activate
pip install -r requirements.txt
mkdir -p work
export SQLITE=1 DEBUG=1
python manage.py migrate
python manage.py bootstrap
python manage.py create_account developer --email developer@example.org --role Директор
python manage.py runserver
```

SQLite — дополнительный режим разработки; production и CI используют PostgreSQL. Для локального PostgreSQL уберите SQLITE и установите DATABASE_URL. DEBUG=1 нужен для локального HTTP; production cookies имеют Secure. При тестировании PostgreSQL без Redis укажите TESTING=1 (подменяет только cache).

Frontend: `npm ci && mkdir -p work && npm run build`. Собранный `static/app.css` включён в git, Node в runtime не нужен. Исходный дополнительный стиль — `static/custom.css`. HTMX отвечает за поиск без полной перезагрузки; Alpine — мобильную навигацию.

## Модули

- Пользователи: Django personal accounts, обязательное подключение TOTP, серверная проверка прав, несколько ролей через группы.
- Клиенты: компании, ИНН (10/12 цифр), реквизиты, контакты, менеджеры, поиск по названию/ИНН, фильтр по менеджеру.
- Сети: несколько связанных клиентов (юридических лиц); форматы принадлежат сети, регионы — общий справочник. Магазин: сеть, необязательные юрлицо/регион/формат, адрес и уникальный код внутри сети. Юрлицо магазина выбирается только из связанных с сетью; зависимые поля обновляются при смене сети.
- Проекты: клиент, менеджер, несколько магазинов, статусы, комментарии, документы; карточка со связанными данными.
- Задачи: исполнитель, срок, приоритет, статусы, переназначение, просрочки, история изменений.
- Документы: случайные имена, whitelist расширений, лимит 10 МБ, приватный volume, скачивание как attachment после проверки прав документа и связанных сущностей; пути не возвращаются в API.
- Уведомления: персональный центр, отметка прочтения, уведомления назначений и просрочек (Celery Beat каждые 5 минут, дедупликация). Интерфейс `NotificationChannel` для будущих адаптеров, внешняя доставка пока отсутствует.
- Аудит: создание, изменение, удаление, импорт, скачивание, успешные этапы входа; before/after, автор и время. Финансовые тексты, реквизиты и контактные данные редактируются в аудите. Журнал доступен в настройках, история — в карточках для уполномоченных пользователей.
- Главная: реальные счётчики БД, проекты, просроченные задачи.

### Матрица доступа

| Роль | Права |
|---|---|
| Директор | Все операции CRM, финансовое разрешение, чтение аудита, создание сотрудников со всеми ролями |
| РОП | CRUD CRM, без финансов и журнала аудита |
| Менеджер | Чтение/создание/изменение CRM, без удаления, финансов и журнала аудита |
| Инженер | Чтение проектов/магазинов/сетей/задач/документов/комментариев, изменение задач, создание/изменение комментариев |
| Администратор | Все операции CRM, чтение аудита, создание сотрудников без назначения директора; без финансов |

Права суммируются для нескольких ролей. Отдельное разрешение `crm.view_finance` разрешает чтение и изменение `financial_notes`; проверяется в HTML и API. Назначенный менеджер — атрибут ответственности: на этапе A нет изоляции записей по владельцу, роли имеют доступ ко всем записям разрешённых модулей. Личные уведомления изолированы по пользователю. Пользователи без роли не видят данные CRM. Superuser — доверенный технический оператор с полными правами; ему также требуется TOTP. Интерфейс Django admin намеренно не подключён.

Аккаунты создаются в «Настройки → Добавить сотрудника» (директор/администратор) или командой `create_account`; несколько ролей назначаются при создании. Доступ к этой операции защищён разрешением `crm.manage_employees`, 2FA и CSRF. Администратор без `crm.view_finance` не может назначать роль директора. Пароль проверяется валидаторами Django, не попадает в аудит, staff/superuser через форму не назначаются. Роли обновляются идемпотентной командой `bootstrap`. Изменение ролей/блокировка существующих пользователей выполняется доверенным оператором через Django shell; редактирование/блокировка существующих аккаунтов через UI в задачу 001.1 не входит. При утрате TOTP доверенный оператор удаляет устройство пользователя через shell, завершает его сессии и регистрирует операцию в AuditEvent; автоматического сброса по email нет. Изменения напрямую через shell/SQL не перехватываются приложением.

### Импорт магазинов

`/stores/import/`, XLSX до 2 МБ, не более 1000 строк, распакованный архив до 20 МБ. Заголовки строго: `Сеть | Код | Название | Адрес | Регион | Формат`. Сеть обязательна; регион и формат необязательны. Регион выбирается из общего справочника без учёта регистра и пробелов, формат должен существовать в выбранной сети. Импорт сохраняет прежние шесть колонок, поле юрлица при импорте остаётся пустым. Код храните в Excel как текст для сохранения начальных нулей. Любая ошибочная строка отменяет весь импорт; дубликаты не обновляются автоматически.

### API

Session authentication + CSRF + подтверждённая TOTP-сессия, тех же серверных прав достаточно и для HTML. Базовый URL `/api/` с ресурсами:
`companies`, `contacts`, `chains`, `regions`, `formats`, `stores`, `projects`, `tasks`, `documents`, `comments`.
GET / POST / PUT / PATCH / DELETE; списки по 30 записей. Загрузка документов — multipart POST; скачивание только `/documents/<id>/download/`. Финансовые поля скрыты без специального разрешения; попытка изменить их через API возвращает 403. История аудита не имеет API для редактирования/удаления. Справочник пользователей не публикуется.

## Проверки

```sh
SQLITE=1 DEBUG=1 pytest
# PostgreSQL (пользователь должен иметь CREATEDB для тестовой базы):
DATABASE_URL=postgresql://crm:password@localhost:5432/crm DEBUG=1 TESTING=1 pytest
python manage.py makemigrations --check --dry-run
python manage.py check
```

Тесты проверяют пароль/TOTP, первичную настройку и replay кода, анонимный доступ, отсутствие роли, несколько ролей, финансовые права, CRUD HTML/API, связи магазинов, переназначение/историю, защищённые файлы, изоляцию уведомлений, импорт с rollback, CSRF, аудит, миграции и страницы. GitHub Actions выполняет тесты с PostgreSQL 17 и Python 3.12. Результаты текущего прогона — `docs/validation.md`.

## Резервное копирование

```sh
scripts/backup.sh backups/manual
# Восстановление только из доверенного архива, заменяет БД:
CONFIRM_RESTORE=YES scripts/restore.sh backups/manual
```

Архив содержит pg_dump custom format и приватные файлы. Перед согласованным backup остановите запись: `docker compose stop web worker beat`, затем запустите backup и возобновите сервисы. Настройте внешнее расписание, шифрование архивов и хранение вне сервера. `.env` и ключи резервируются отдельно защищённым способом. Restore останавливает web/worker/beat; при ошибке они остаются остановленными для проверки оператором.

## Границы этапа A

БП-01/БП-02 не реализованы: предусмотрены базовые сущности, права, статусы и сервисный слой. БП-03 и следующие процессы отсутствуют. Нет самостоятельных договоров, логистики, монтажа, бухгалтерии, банковских интеграций, Telegram/Email доставки. Нет финансового учёта: отдельное защищённое текстовое поле демонстрирует границу финансового доступа.

Это основа для внутреннего пилота после настройки инфраструктуры и ролей. До промышленной эксплуатации нужны согласование матрицы доступа, политика восстановления 2FA и паролей, антивирусная проверка файлов (сейчас есть ограничения типа/размера, скачивание принудительное), мониторинг, квоты хранилища, offsite backup и регулярная проверка восстановления. Полнотекстовый поиск, расширенная фильтрация API и страницы списков свыше 200 строк оставлены на следующий этап; API имеет пагинацию. Не проводился нагрузочный тест или независимый аудит безопасности.

## Отдельная интеграционная проверка Compose

Workflow `.github/workflows/compose.yml` (`Compose integration`) работает на временном GitHub-hosted Ubuntu runner. Использует основной `compose.yaml` плюс `compose.ci.yaml`: те же образы и процессы, но HTTP Caddy на loopback-портах 18080/18081, один процесс worker, интервал Beat 5 секунд вместо 300. `DEBUG=0`, локальные статические файлы обслуживает WhiteNoise через Caddy/Gunicorn. Публичный домен не требуется; TLS здесь не проверяется.

Сценарий `scripts/ci/compose_smoke.py` запускает web, PostgreSQL, Redis, Worker, Beat и Caddy, проверяет healthchecks, миграции, статические файлы по SHA-256, закрытые URL, сессию с подтверждённой 2FA, скачивание документа, реальный запуск задачи worker и отдельное планирование Beat. Затем останавливает запись в исходном тестовом проекте, вызывает `backup.sh`, восстанавливает PostgreSQL и media через `restore.sh` в другом новом проекте, сверяет записи, связи и SHA-256 каждого media-файла; повторно проверяет исходный проект. Рабочие и production-данные не используются. В сценарии нет очистки Docker/томов; временные ресурсы исчезают при завершении runner. В artifacts попадают только диагностические `.log`, не `.env`, архивы или cookies.

Параметры Compose для изоляции: `CRM_ENV_FILE` (по умолчанию `.env`), `CRM_IMAGE`, `CRM_BIND_ADDRESS`, `CRM_HTTP_PORT`, `CRM_HTTPS_PORT`, стандартные `COMPOSE_PROJECT_NAME` / `COMPOSE_FILE`. Исходный и восстановленный проекты используют разные автоматически именованные volumes. `backup.sh` отказывается перезаписывать существующий каталог резервной копии. Не запускайте destructive restore на рабочей БД ради проверки: используйте новый проект/сервер. Скрипт CI намеренно отказывается запускаться вне GitHub Actions.

TLS на VPS проверяется отдельно после назначения DNS и доступности 80/443: получить публичный сертификат Caddy, проверить `https://<домен>/health/` с обычной проверкой цепочки доверия, HTTP→HTTPS redirect, вход/2FA и Secure cookies, CSRF и защищённое скачивание. Результат CI с HTTP не подтверждает эту часть.

## TASK 001.1 — доработки и обновление Codespaces

- В настройках доступны список сотрудников и создание персонального аккаунта с несколькими ролями. Новый сотрудник подключает собственную TOTP при первом входе. Ответственный менеджер клиента выбирается из активных сотрудников с отображением имени и логина; уже назначенный неактивный сотрудник сохраняется до ручного переназначения.
- В торговой сети можно выбрать несколько юрлиц; их список показан в карточке. Юрлицо магазина необязательно и должно быть связано с его сетью. Удалить эту связь сети с юрлицом нельзя, пока на неё ссылается магазин.
- В форме магазина кнопка «Новый формат для выбранной сети» открывает окно создания: после сохранения формат выбран автоматически, введённые поля магазина остаются на месте. Отмена также возвращает к заполнению. Формат необязателен.
- Четыре карточки главной страницы ведут к соответствующим спискам.

### Миграция регионов

Миграция `0002` не удаляет существующие сети, магазины, клиентов или строки регионов. Для общего справочника названия сравниваются через Unicode casefold с исключением всех пробельных символов: `Москва`, ` МОСКВА ` и `Мо ск ва` совпадают. Для каждой группы совпадений активным становится регион с минимальным ID. Остальные строки остаются архивными aliases (`canonical`), скрытыми из UI/API и выбора. Магазины переводятся на активный регион; предыдущие ID сохраняются в событиях `region_consolidated`. `legacy_data` сохраняет исходные название и ID сети каждого региона. Форматы, ID магазинов и связи проектов не меняются. Уникальный нормализованный ключ защищён ограничением БД. Новые связи сеть↔юрлица автоматически не угадываются; заполните их вручную. Перед обновлением сделайте резервную копию.

### Ручная приёмка

1. Войти директором с TOTP. В настройках создать сотрудника с ролями менеджера и инженера; войти им в отдельном браузере и убедиться, что требуется настройка собственной TOTP.
2. В карточке клиента выбрать нового сотрудника ответственным менеджером и сохранить.
3. В сети выбрать несколько юрлиц, проверить их в карточке. В магазине после выбора сети доступны только эти юрлица, поле можно оставить пустым.
4. Выбрать общий регион в магазинах двух сетей. Попробовать создать вариант названия с другим регистром/пробелами — форма должна отказать.
5. Заполнить магазин, создать формат во всплывающем окне, убедиться, что данные сохранены и новый формат выбран. Проверить также сохранение магазина без формата.
6. На главной открыть все четыре карточки показателей. Повторить основные действия на смартфоне.

`pytest` проверяет новые права/формы/API и миграцию из 0001 с существующими данными. В Compose integration добавлен Chromium-сценарий `scripts/ci/task0011_browser.cjs`: компьютер 1440×1000 и смартфон 390×844, сотрудники/роли, менеджер, юрлица сети, зависимые поля, формат без потери ввода и ссылки показателей. Сессия тестового директора заранее подтверждена probe; сам процесс пароль/TOTP покрыт отдельными pytest и прежней браузерной проверкой. В artifacts сохраняются логи и скриншоты, но не cookies/fixtures.
